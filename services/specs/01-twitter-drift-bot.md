# 01 — X/Twitter drift bot (build #1)

Status: build-ready. Depends on spec 02's output shape (`findings.json` / the bot-facing findings
table) but can be built and tested against a fixture before spec 02 exists, since the interface is
fixed below.

## 1. Purpose (reframed, R14)

**Public oracle, not content poster.** The primary mode is invoke-reply: anyone tweets
`@skillsdrift scan <repo-url>` and the bot replies with that repo's drift **card** — a link to
`build/scanner/out/cards/<slug>.html` (or its hosted equivalent once DNS exists). Every invocation
is user-initiated and public — the asker's own followers see the reply, which is the actual
distribution mechanism, not the weekly cadence. The card is generated by `build/cardgen/`, fed by
a `build/scanner/scan-repo.js` run against the requested repo — this spec is a thin reply layer on
top of a scanner interface that already exists as of R14, not a standalone content generator.

The weekly ecosystem delta (`build/scanner/weekly-delta.js` output) is the **secondary** broadcast
layer: a scheduled thread summarizing "this week: N new drifted, M newly orphaned" across the
living index, framed as drafts per the human-review gate below — never auto-posted. See
`strategy/launch-distribution-ideas.md` idea N7 (verdict: KILL as a *launch* mechanism, valid only
as Day 7-30+ tail content) — the weekly-delta broadcast implements exactly that tail role; the
scan-reply oracle is the new primary mode this round reframes toward.

**R14 implementation note:** the scanner/card interface this spec depends on is now real
(`build/scanner/scan-repo.js`, `build/cardgen/cardgen.js` — see `02-ecosystem-scanner.md` and
`03-shareable-report-card.md`), not just a fixed fixture contract. `bot-findings-table.json` (§4)
should be regenerated from a live `scan-repo.js`/`scan-list.js` run rather than only a fixture once
this spec is built; the fixture-based contract below remains the correct interface to build against
in the interim (no X credentials exist yet either way — see `00-feasibility-notes.md`).

## 2. Binding constraints (do not weaken)

- **Human review gate is mandatory.** Nothing reaches the X API without a human reading and
  approving it first. This is a process constraint, not a suggestion — the `post` command
  structurally cannot run against a draft that hasn't been marked approved (§5).
- **No shaming of maintainers.** Per R9's N3 verdict, the bot reports drift *statistics* and
  *findings* on large public repos factually. When a specific repo is named, it is framed as
  "found in our scan of public skill repos — common pattern," never "X repo did Y wrong."
  Individual maintainers/authors are never named or @-mentioned.
- **T5 recurrence close, tweet-length, on every thread.** The strategic point (a scan finds it,
  only governance prevents recurrence) must survive compression to ~280 chars.
- **Disclosure on every thread.** One tweet, every thread, no exceptions: candidate-exercise
  disclosure (see template §4).
- **No fabricated posting.** `post` mode without real X credentials must fail with a clear,
  specific error. Never write a stub that pretends to post and logs "success."

## 4. Data flow and the spec-02 interface

Input: `data-drop/findings.json` produced by the ecosystem scanner (spec 02 §3), plus
`data-drop/bot-findings-table.json` — a flattened, bot-specific slice spec 02 also writes,
containing only what a thread needs:

```jsonc
// bot-findings-table.json — the ONLY shape driftbot.js is allowed to depend on
{
  "scanId": "2026-09-26",                 // ISO date of the scan run, also the draft filename stem
  "totalReposScanned": 14,
  "totalSkillsScanned": 412,
  "findings": [
    {
      "kind": "drift" | "security_category" | "ownership" | "duplication",
      "repoSlug": "org/repo",              // public, safe to name for drift/duplication kinds
      "skillName": "pdf-gen",
      "headline": "diverged into 2 versions across forks",   // pre-written, factual, no repo-shaming
      "statLine": "3 versions of pdf-gen found across the sample",
      "severityCategory": "medium" | "high" | "low",
      "nameable": true                     // false for security_category kind (category-level only, never repo-attributed)
    }
  ],
  "aggregateStat": "36% of scanned public skills show at least one governance gap (unowned, unversioned, or drifted)"
}
```

Rule enforced in `thread-builder.js`: if `nameable === false`, the repo slug is dropped from the
tweet text entirely — the finding renders as a category-level stat only. This is the code-level
enforcement of the honesty naming policy (spec 02 §4).

## 5. Modes

```
driftbot draft [--scan-id <id>] [--source <path>]   # default. No network. Writes drafts/<id>.json
driftbot list                                        # shows drafts with status: draft|approved|posted
driftbot approve <id>                                # human marks a draft approved (no content change)
driftbot post <id>                                   # only runs if status === "approved"
```

- `draft` (default): reads `bot-findings-table.json` (from `--source`, default
  `../ecosystem-scanner/data-drop/latest/bot-findings-table.json`), runs `thread-builder.js`,
  writes `drafts/<scanId>.json` (see schema §6). Exit 0 always (pure local file op). No network
  call of any kind.
- `list`: prints draft id, status, tweet count, generated-at. Read-only.
- `approve <id>`: flips `status` from `draft` → `approved` in the draft file. This is the review
  gate. A human must run this command by hand after reading the draft file's `tweets[]` array
  (or after editing it directly — edits are preserved, `approve` does not regenerate content).
- `post <id>`: refuses (exit 2, message `"draft <id> is not approved — run 'driftbot approve <id>' after a human reviews drafts/<id>.json"`) unless status is `approved`. If approved, calls the configured `AuthProvider.postThread(tweets)`. With the shipped `null-provider` (default, no config), this fails with:
  `"No X API credentials configured. Set XURL_BEARER_TOKEN (or configure src/auth/xurl-provider.js) before running 'post'. See README.md#auth-provider."`
  This is the expected, correct behavior on this VPS today (per `00-feasibility-notes.md` — no X
  creds exist). `post` must never silently no-op or fabricate a success response.

## 6. Draft file schema (`drafts/<scanId>.json`)

```jsonc
{
  "scanId": "2026-09-26",
  "generatedAt": "2026-09-26T09:00:00.000Z",
  "status": "draft",              // draft -> approved -> posted
  "approvedAt": null,
  "approvedBy": null,             // free-text, set by the human running `approve`, e.g. "aryaman"
  "postedAt": null,
  "tweets": [
    "1/ Ran the drift scanner across 14 public skill repos this week. 36% of scanned public skills show at least one governance gap. Thread 🧵",
    "2/ pdf-gen: found 3 diverged versions across the sample — common pattern when skills get copy-pasted instead of shared from one source.",
    "3/ ...",
    "N/ This recurs the moment anyone edits a copy again — a scan finds it, only a governed source stops it from coming back.",
    "N+1/ Part of a candidate exercise for Atlan, not an Atlan product. Full findings + methodology: <repo-link>"
  ]
}
```

## 7. Thread template (with real variables)

`src/template.js` exports these template strings; `thread-builder.js` fills them from the
`bot-findings-table.json` shape in §4. Variables in `{braces}`.

```
HOOK:
  "Ran the drift scanner across {totalReposScanned} public skill repos this week. {aggregateStat}. Thread 🧵"

FINDING_DRIFT (nameable=true):
  "{skillName}: {headline} — found in our scan of public skill repos, common pattern when a skill gets copy-pasted instead of shared from one source."

FINDING_DRIFT (nameable=false, category fallback — should not normally occur for drift kind):
  "{statLine}"

FINDING_SECURITY_CATEGORY (always nameable=false):
  "{statLine} — category-level only; we don't call out specific repos for security findings."

FINDING_OWNERSHIP:
  "{statLine} — no named owner means no one to ask when it breaks."

FINDING_DUPLICATION (nameable=true):
  "{skillName} shows up in {n} places across the sample with {versionCount} different versions live at once."

RECURRENCE_CLOSE:
  "This recurs the moment anyone edits a copy again — a scan finds it, only a governed source stops it from coming back."

DISCLOSURE (always last tweet):
  "Part of a candidate exercise for Atlan, not an Atlan product. Full findings + methodology: {repoLink}"
```

Thread assembly order: HOOK, then 3-6 FINDING_* tweets (one per `findings[]` entry, capped at 6,
prioritized security_category and drift kinds first), then RECURRENCE_CLOSE, then DISCLOSURE.
Minimum thread length enforced by `thread-builder.js`: 5 tweets (hook + ≥1 finding + close +
disclosure); if fewer than 1 finding exists, `draft` exits 2 with "not enough findings to draft a
thread — check --source path."

## 8. Auth-provider interface

```js
// src/auth/provider.js
export class AuthProvider {
  /** @returns {Promise<void>} throws NotConfiguredError or PostError */
  async postThread(tweets) { throw new Error('not implemented'); }
}
export class NotConfiguredError extends Error {}
```

`null-provider.js` (default, always shipped, always active until config says otherwise):
throws `NotConfiguredError` with the message in §5.

`xurl-provider.js` (present in the repo, inert): wraps shelling out to the `xurl` binary (X's
official OAuth2 CLI) or an equivalent HTTP call to the X API v2 `POST /2/tweets` /
thread-reply-chain endpoints. Reads `XURL_BEARER_TOKEN` (or whatever env var Aryaman's chosen
auth path uses) from env. Selected via `config.json`'s `"authProvider": "xurl"` — default is
`"null"`. This file can be written and unit-tested (with a mocked shell call) without any real
credentials; it simply cannot be exercised end-to-end until creds exist (00-feasibility-notes.md
blocking item #1).

## 10. Test plan (no network tests)

`test/run-tests.sh` runs all `*.test.js` under `test/` using Node's built-in test runner
(`node --test`), no dependency added.

1. **Golden-file: thread generation.** `fixtures/sample-findings.json` (shape-matches §4, 4
   findings: 1 drift nameable, 1 security_category, 1 ownership, 1 duplication) → run
   `thread-builder.js` → assert output tweets array equals a checked-in `fixtures/expected-
   thread.json` exactly (byte-for-byte after JSON normalization).
2. **Nameable enforcement.** Fixture with a `nameable: false` drift-kind finding → assert the
   repo slug string never appears in any tweet in the output.
3. **Minimum-length guard.** Empty `findings[]` → assert `draft` exits 2 with the documented
   message.
4. **Disclosure presence.** Every generated thread fixture → assert the last tweet matches the
   DISCLOSURE template exactly (string includes "candidate exercise for Atlan").
5. **Review-gate enforcement.** Draft written with `status: "draft"` → `post <id>` invoked
   programmatically → assert it throws/exits before `AuthProvider.postThread` is ever called
   (spy/mock the provider, assert zero calls).
6. **Auth failure path.** `post` on an `approved` draft with default `config.json` (null
   provider) → assert exit code non-zero and the exact NotConfiguredError message from §5. No
   network call attempted (assert via a mock that throws if `fetch`/`child_process` is invoked).

All 6 cases run offline; nothing in this test plan touches the network or requires X credentials.
